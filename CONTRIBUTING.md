# Contributing

## The workflow

1. Branch off `main`: `git checkout -b contract/offers-add-terms-url`
2. Edit the spec(s) under `specs/`.
3. `npm run check` — this lints, bundles, **and regenerates both the Kotlin
   models and the Dart clients**. Commit the `generated/` changes along with the
   spec change; CI fails if they drift apart.
4. Open a PR using the template. Say who consumes the change.
5. CODEOWNERS pulls in the owning team and the API reviewers. Needs one approval
   from each.
6. On merge, the Swagger UI on GitHub Pages rebuilds automatically.

Frontend and backend engineers are equal contributors here. A frontend engineer
proposing the shape they need is a normal, expected PR — it just needs the owning
backend team's approval before merge.

## What reviewers look for

- **Is it consistent?** Naming, pagination, error shape, money representation
  match the conventions in the README.
- **Is it backwards compatible?** If not, is the version bump and migration
  plan spelled out?
- **Are the examples real?** `"ada@example.com"`, not `"string"`.
- **Are the errors documented?** Which 4xx can a client actually receive, and
  with which `code`?
- **Is it reusing `specs/shared/components.yaml`?** A redefined `Error` schema
  is a review comment.

## How a service spec is laid out

Only `specs/<service>/openapi.yaml` is required — that path is what discovery globs
(`scripts/build-site.mjs`, and the `breaking-changes` CI job). Everything else is yours to
organise. Redocly inlines every relative `$ref` at bundle time, so the generators only ever
see the flattened `dist/specs/<service>.yaml` and never observe your directory layout.

A single file is fine, and is the right default. Split it once it stops being scannable —
roughly 500+ lines, or when two people keep colliding in it. `specs/offers/` is the worked
example:

```
specs/offers/
  openapi.yaml                  # info, servers, security, tags, securitySchemes; paths are $refs
  paths/
    offers.yaml                 # one file per path item
    offers-by-id.yaml
  components/
    parameters.yaml
    schemas/
      Offer.yaml
```

Three rules make the split behave:

1. **Refs resolve against the file they are written in, not the root document.** Inside
   `paths/offers.yaml`, shared components are `../../shared/components.yaml`, not
   `../shared/...`. And a root-document pointer like `#/components/schemas/Offer` silently
   resolves against the path file itself — use `../components/schemas/Offer.yaml` instead.

2. **The bundled component name comes from the file name**, and that name becomes the
   generated Kotlin/Dart class. `components/schemas/Offer.yaml` bundles to `Offer`. Name the
   file exactly what you want the class called.

3. **Do not also declare the component in `openapi.yaml` as an alias.** Writing
   `schemas: { Offer: { $ref: './components/schemas/Offer.yaml' } }` emits *two* schemas into
   the bundle — `Offer` as a pointer plus a filename-derived duplicate. Let the `paths/` files
   pull components in on their own.

Name your response envelopes. An inline `200` body gets an autogenerated name from the
operation — `ListOffers200Response` — and Fabrikt skips it entirely, so Kotlin consumers get
no type at all. `components/schemas/OfferPage.yaml` exists for that reason.

Splitting a spec is meant to be a zero-diff refactor. Verify it: snapshot `dist/specs/` and
`generated/` before, run `npm run check`, and confirm `generated/` is unchanged.

## Schema rules the generator imposes

Fabrikt is stricter than the OpenAPI spec. The one that bites:

> `'User' schema contains an invalid combination of properties and
> `oneOf | anyOf | allOf`. Do not use properties and a combiner at the same level.`

Valid OpenAPI, rejected by Fabrikt. Put everything inside the `allOf`:

```yaml
# Won't generate
User:
  type: object
  properties: { id: { type: string } }
  allOf:
    - $ref: '../shared/components.yaml#/components/schemas/Timestamps'

# Will generate
User:
  allOf:
    - $ref: '../shared/components.yaml#/components/schemas/Timestamps'
    - type: object
      properties: { id: { type: string } }
```

`npm run generate:kotlin` prints this hint when it hits the case. Redocly lint
will *not* catch it — only the codegen step does.

The Dart generator is more permissive but quieter: unsupported `format` values
(`email`, and others) silently degrade to `String`, and only the first `servers:`
entry becomes the client `basePath`. Unlike Kotlin, it *does* honour `required` —
a required property is non-nullable in Dart, so adding or removing one from
`required:` is a source-breaking change for Flutter consumers.

## Breaking changes

CI runs `oasdiff breaking` against the base branch and fails the PR if it finds
one. That failure is a prompt to talk, not a wall: if the change is agreed, bump
the path version (`/v1` → `/v2`) or, for a genuinely coordinated break, get
explicit sign-off from every consumer in the PR thread and note it in the
description.

## Don't

- Don't commit anything under `dist/` — it is generated.
- Don't edit a spec to match an implementation that already shipped and diverged.
  Fix the implementation, or PR the contract change on its own and explain why.
